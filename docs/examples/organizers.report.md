## Как агент нарезал требования

Спецификация описывает функцию мобильного банка для уведомления клиента о достижении месячного порога расходов по карте. Содержит требования к UI, расчету расходов и дочернюю спецификацию REST API для управления настройками порога.

#### D-012. Использование метода GET для изменения данных

Критерий: соответствие шаблону (ISO/IEC/IEEE 29148:2018, п. 5.2.5) · Серьёзность: существенный · Требования: R-016, R-020

Спецификация описывает метод сохранения и изменения порога как HTTP-запрос GET. По стандартам REST метод GET должен использоваться только для безопасного чтения и быть идемпотентным, а изменение данных должно выполняться методами POST, PUT или PATCH.

> «Description · Сохранение порога. Функциональные требования: чтение порога» — строка 103

**Как исправить.** Изменить тип метода с GET на POST или PUT.

**Сведено в эту находку** (редактор счёл это тем же дефектом):

- Использование GET для изменения данных — соответствие шаблону (ISO/IEC/IEEE 29148:2018, п. 5.2.5), существенный. Метод предназначен для сохранения порога, но использует HTTP-метод GET. Использование GET для изменения состояния на сервере нарушает стандартную семантику REST и HTTP-методов, согласно которой GET должен быть безопасным.

Термин «проведённые покупки» может означать как успешно авторизованные операции (холдирование), так и операции, прошедшие финансовое списание (клиринг). #### D-014. Противоречие в коде ответа при ошибке валидации

Критерий: непротиворечивость (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.4) · Серьёзность: существенный · Требования: R-019, R-021, R-031, R-032

Раздел «Статусы» указывает, что при неверных параметрах возвращается код 400. Однако в примере для успешного кода 200 показан ответ с результатом ERROR и сообщением об ошибке суммы. Неясно, какой HTTP-код (200 или 400) должен возвращать сервис при попытке сохранить сумму вне допустимого диапазона, что приведет к рассинхронизации обработки ошибок между клиентом и сервером.

> «При отклонении суммы вернуть прежнее состояние и результат ERROR.» — строка 121

> «Ответ в случае, если параметры запроса заполнены неверно.» — строки 162–163

> «{"result":"ERROR","message":"Проверьте сумму"}» — строки 170–172

> «Ответ в случае успешного выполнения метода.» — строки 162–163

**Как исправить.** Перенести пример ответа с ошибкой валидации из описания кода 200 в код 400. В пункте 5 раздела «Логика работы метода» заменить возврат результата ERROR на возврат HTTP-статуса 400. В таблице параметров ответа для поля result убрать значение ERROR.

**Сведено в эту находку** (редактор счёл это тем же дефектом):

- Неоднозначное условие для кода 400 — однозначность (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.2), существенный. Фраза «заполнены неверно» допускает разные трактовки. Один разработчик может возвращать 400 при нарушении бизнес-правил (например, сумма вне лимита), а другой — только при технических ошибках (отсутствие обязательного параметра или неверный тип данных).
- Ошибка валидации возвращается с HTTP-статусом 200 — непротиворечивость (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.4), существенный. Описание статус-кодов указывает, что 200 означает успех, а 400 — ошибку параметров. Однако в примере для успешного ответа (200) приведен JSON с ошибкой валидации суммы. HTTP-статусы и бизнес-результаты противоречат друг другу, что сломает обработку ошибок на клиенте.

**Вопрос автору.** Какой HTTP-статус должен возвращаться, если сумма не проходит проверку: 200 с бизнес-ошибкой или 400 Bad Request?

#### D-020. Не указан URL для продуктового контура

Критерий: полнота набора (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: незначительный · Требования: R-016

В спецификации API указан адрес метода только для среды разработки (Dev), а значение для продуктовой среды (Prod) оставлено пустым. Это незаполненное поле шаблона не мешает разработке, но потребует уточнений при настройке релиза приложения.

> «Dev: /alerts/saveLimit . Prod: —» — строка 108

**Как исправить.** Заполнить значение URL для Prod-контура, например: `/api/v1/alerts/saveLimit`.
