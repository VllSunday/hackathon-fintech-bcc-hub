## Как агент нарезал требования

Документ содержит требования к реализации функции мобильного банка для уведомления клиентов о достижении заданного месячного порога расходов по карте. Включает описание бизнес-процесса, функциональные требования и дочернюю спецификацию REST API для управления настройками порога.

Части документа: «Часть A. Новый функционал» — основная спецификация; «Часть B. REST API» — дочерняя спецификация, детализирует «Часть A. Новый функционал».

Термин «исходный итог» допускает два толкования. Первое: система обеспечивает идемпотентность, и дубликат игнорируется, сохраняя сумму, рассчитанную после первой обработки. #### D-010. Использование GET для изменения данных

Критерий: соответствие шаблону (ISO/IEC/IEEE 29148:2018, п. 5.2.5) · Серьёзность: существенный · Требования: R-021, R-025

Метод выполняет замену настроек, но для него указан HTTP-метод GET. Это нарушает конвенции REST API, где GET предназначен только для безопасного чтения данных; изменение состояния через GET может привести к случайным перезаписям при кэшировании запросов или их повторах сетевым оборудованием.

> «REST type · GET» — стр. 3

> «Заменить настройку и вернуть результат сохранения.» — стр. 4

> «Description · Сохранение порога. Функциональные требования: чтение порога» — стр. 3

**Как исправить.** В таблице «Общие параметры» изменить REST type на POST. Удалить флаг -G из примера CURL-запроса и перенести параметры из раздела «Query-параметры» в раздел «Request body».

**Сведено в эту находку** (редактор счёл это тем же дефектом):

- Метод сохранения использует HTTP-метод GET — соответствие шаблону (ISO/IEC/IEEE 29148:2018, п. 5.2.5), существенный. Метод предназначен для сохранения порога, то есть он изменяет состояние на сервере. Однако для него указан HTTP-метод GET, который по конвенциям REST должен использоваться только для безопасных и идемпотентных операций (чтение). Использование GET для изменения данных нарушает общепринятые архитектурные стандарты.

#### D-012. Не указаны условия возврата кода 201

Критерий: полнота (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: существенный · Требования: R-035

Требование называет код 201 успешным, но в документе не описано, при каких условиях API возвращает 200, а при каких — 201. Разработчик бэкенда не сможет реализовать логику выбора между этими статусами, так как триггер для 201 неизвестен.

> «Если результат 200 или 201 — успешный.» — стр. 4

> «Если результат 200 или 201 — успешный. Если результат 400, 401 и далее — неуспешный.» — стр. 4

> «Successful — Created» — стр. 4

**Как исправить.** Исключить упоминание кода 201 из общего правила успешного ответа и переименовать заголовок статуса 200 на «200. Successful — OK», либо добавить четкое условие для возврата 201 (например, при первичном создании порога).

**Сведено в эту находку** (редактор счёл это тем же дефектом):

- Отсутствует спецификация статуса 201 — полнота набора (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.3), существенный. В документе заявлено, что успешный ответ может иметь код 200 или 201. При этом в разделе статусов код 201 не описан, а для кода 200 указан текст «Created», что обычно соответствует 201. Из-за этого разработчикам неясно, какой именно код возвращать при успешном сохранении и требуется ли возвращать 201.

**Вопрос автору.** В каких случаях метод должен возвращать статус 201?

#### D-016. Не указаны тексты сообщений об ошибках

Критерий: полнота (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: незначительный · Требования: R-005

Требование описывает поведение UI при ошибке ввода, но не содержит самих текстов сообщений (например, для пустой суммы или значения вне лимита 1 000–1 000 000 ₸). Тестировщики не смогут проверить правильность выводимых текстов.

> «При ошибке ввода сообщение появляется под полем.» — стр. 1
