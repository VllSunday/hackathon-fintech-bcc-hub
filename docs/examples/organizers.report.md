## Как агент нарезал требования

Спецификация описывает функцию мобильного банка для уведомления клиента о достижении месячного порога расходов по карте. Содержит требования к UI, расчету расходов и дочернюю спецификацию REST API для управления настройками порога.

#### D-001. Многозначность термина «проведённые покупки»

Если разработчики реализуют расчет по клирингу, который происходит через несколько дней, это нарушит прямое требование извещать клиента «в момент покупки».

#### D-012. Использование метода GET для изменения данных

Спецификация описывает метод сохранения и изменения порога как HTTP-запрос GET. По стандартам REST метод GET должен использоваться только для безопасного чтения и быть идемпотентным, а изменение данных должно выполняться методами POST, PUT или PATCH.

> «Description · Сохранение порога. Функциональные требования: чтение порога» — строка 103

**Как исправить.** Определить подходящий HTTP-метод (POST или PUT), указать его в таблице параметров вместо GET и обновить пример cURL, чтобы убрать флаг -G и корректно передать параметры.

**Сведено в эту находку** (редактор счёл это тем же дефектом):

- Использование GET для изменения данных — соответствие шаблону (ISO/IEC/IEEE 29148:2018, п. 5.2.5), существенный. Метод предназначен для сохранения порога, но использует HTTP-метод GET. Использование GET для изменения состояния на сервере нарушает стандартную семантику REST и HTTP-методов, согласно которой GET должен быть безопасным.

**Вопрос автору.** Какой HTTP-метод (POST или PUT) следует использовать для сохранения настроек вместо GET?

#### D-004. Противоречие в лимите уведомлений при изменении порога

**Вопрос автору.** Может ли клиент получить второе уведомление за месяц, если он повысил порог после первого срабатывания?

#### D-006. Отсутствует метод API для чтения настроек

Критерий: непротиворечивость (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.4) · Серьёзность: критичный · Требования: R-002, R-011, R-016, R-020, R-026

Часть А требует, чтобы приложение читало настройки через REST API, и в описании метода заявлено чтение. Однако единственный описанный метод `/alerts/saveLimit` и его логика предполагают только сохранение (замену) порога. Неясно, каким образом приложение должно получать текущие настройки при открытии экрана уведомлений.

> «Request URL · Dev: /alerts/saveLimit . Prod: —» — строка 108

> «Заменить настройку и вернуть результат сохранения.» — строка 120

**Как исправить.** Выбрать и описать способ чтения настроек: добавить отдельный метод (например, GET /alerts/getLimit) или явно указать, как использовать существующий метод saveLimit без перезаписи данных.

**Сведено в эту находку** (редактор счёл это тем же дефектом):

- В спецификации API отсутствует метод чтения настроек — полнота набора (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.3), критичный. Часть A требует, чтобы мобильное приложение читало и отображало текущие настройки пользователя и сумму расходов за месяц. Однако в спецификации REST API (Часть B) описан только метод сохранения `/alerts/saveLimit`, а метод для получения данных отсутствует. Архитектура и бизнес-процесс требуют получения сохраненного порога для проверки при покупке и отображения в приложении. Однако в спецификации API описан только метод сохранения (saveLimit), без которого функционал чтения и проверки расходов реализовать невозможно.
- Отсутствует метод API для чтения настроек — полнота набора (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.3), критичный. Основной документ требует, чтобы приложение читало и сохраняло настройки через API, и спецификация API заявляет чтение в описании. Однако в спецификации описан только метод сохранения порога (`saveLimit`), а метод для чтения отсутствует. Разработчики мобильного приложения не смогут реализовать инициализацию экрана настроек.
- Чтение порога требует обязательной перезаписи — непротиворечивость (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.4), критичный. В описании метода заявлено выполнение функционального требования по чтению порога. При этом параметры amount и enabled указаны как обязательные, а логика метода всегда выполняет замену настройки. Клиент не может запросить текущие настройки порога, не передав новые значения, что делает безопасное чтение невозможным.

#### D-013. Противоречие в составе полей при ошибке сохранения

#### D-014. Противоречие в коде ответа при ошибке валидации

Критерий: непротиворечивость (ISO/IEC/IEEE 29148:2018, п. 5.2.6; IEEE Std 830-1998, п. 4.3.4) · Серьёзность: существенный · Требования: R-019, R-021, R-031, R-032

Раздел «Статусы» указывает, что при неверных параметрах возвращается код 400. Однако в примере для успешного кода 200 показан ответ с результатом ERROR и сообщением об ошибке суммы. > «{"result":"ERROR","message":"Проверьте сумму"}» — строки 170–172

**Как исправить.** В пункте 5 раздела «Логика работы метода» и в описании полей ответа указать использование HTTP 400 для ошибок валидации суммы, удалить статус ERROR из возможных значений result и убрать пример ошибки из блока 200 ответа.

**Вопрос автору.** Какой HTTP-статус должен возвращаться, если сумма не проходит проверку: 200 с бизнес-ошибкой или 400 Bad Request?

#### D-016. Статус 201 указан как успешный, но не описан

Если при первом сохранении нужен 201, добавить для него отдельный заголовок, описание и пример ответа в раздел «Статусы».

#### D-020. Не указан текст push-уведомления

Критерий: полнота (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: незначительный · Требования: R-006

В требовании сказано, что клиент получает уведомление, но не задан его текст. Разработчикам неизвестно, какие именно слова и переменные (например, сумму или маску карты) выводить в сообщении, чтобы клиент понял суть уведомления.

> «Ф-3. Когда расходы переходят от суммы ниже порога к сумме, равной порогу или выше, клиент получает push.» — строка 39

**Как исправить.** В разделе «Функциональные требования» указать точный шаблон текста push-уведомления с переменными, например: «Превышен лимит расходов. Месячная сумма достигла {amount} ₸».
