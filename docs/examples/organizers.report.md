### Замечания к отдельным требованиям

#### D-004. Неясно, какая сумма передаётся в push

Критерий: однозначность (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.2) · Серьёзность: критичный · Требования: R-008

Слово «сумму» можно интерпретировать по-разному: это может быть сумма текущей операции (покупки), общая сумма накопленных расходов за месяц или размер установленного порога. Неясно, какое значение сервис расходов должен передавать для отправки.

> «Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога.» — строка 43

**Как исправить.** Уточнить, какая именно сумма передаётся, например: «...и накопленную сумму расходов за месяц при достижении порога».

**Вопрос автору.** Какую сумму нужно передавать в сервис push: сумму последней покупки, общие расходы за месяц или сам порог?

#### D-007. Нет правила для нового порога ниже текущих расходов

Критерий: полнота (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: существенный · Требования: R-007

Требование Ф-4 описывает логику только для случая, когда накопленная сумма строго ниже нового порога. Неясно, как должна вести себя система, если пользователь задает порог, который уже равен текущим расходам или меньше их: отправить push немедленно при сохранении настройки или не отправлять ничего.

> «При изменении порога накопленная сумма сохраняется. Если она ниже нового порога, следующее достижение вызывает push независимо от истории предыдущей настройки.» — строка 40

**Как исправить.** Дополнить Ф-4 правилом: «Если накопленная сумма равна новому порогу или превышает его, push-уведомление в момент сохранения не отправляется».

**Вопрос автору.** Нужно ли отправлять push при сохранении порога, если расходы месяца уже равны ему или превышают его?

#### D-008. Использование метода GET для изменения данных

Критерий: соответствие шаблону (ISO/IEC/IEEE 29148:2018, п. 5.2.5) · Серьёзность: существенный · Требования: R-016, R-020

Спецификация описывает метод сохранения и изменения порога как HTTP-запрос GET. По стандартам REST метод GET должен использоваться только для безопасного чтения и быть идемпотентным, а изменение данных должно выполняться методами POST, PUT или PATCH.

> «REST type · GET» — строка 104

> «Заменить настройку и вернуть результат сохранения.» — строка 120

> «Description · Сохранение порога. Функциональные требования: чтение порога» — строка 103

**Как исправить.** Изменить тип метода с GET на POST или PUT.

**Вопрос автору.** Какой HTTP-метод (POST или PUT) следует использовать для сохранения настроек вместо GET?

#### D-012. Отсутствует формат ответа для статуса 403 Forbidden

Критерий: полнота (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: существенный · Требования: R-034, R-036

Статус 403 указан в списке возможных ответов метода, однако его описание и пример тела ответа пропущены. В разделе 403 вместо этого приведено описание статуса 404, что оставляет структуру ошибки 403 неизвестной для разработчиков.

> «Ответ в случае, если на указанный ресурс доступ запрещен.» — строки 174–176

> «#### 403. Unsuccessful — Forbidden» — строка 188

> «Для чужой карты возвращается 404, как и для отсутствующей карты.» — строки 189–190

**Как исправить.** Добавить пример JSON-ответа для статуса 403 или исключить этот статус из списка, если при ошибке доступа используется только 404.

**Вопрос автору.** Какое тело ответа должно возвращаться при статусе 403?
