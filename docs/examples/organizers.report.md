### Замечания к отдельным требованиям

#### D-001. Многозначность термина «проведённые покупки»

Критерий: однозначность (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.2) · Серьёзность: критичный · Требования: R-003, R-005

Термин «проведённые покупки» может означать как успешно авторизованные операции (холдирование), так и операции, прошедшие финансовое списание (клиринг). Если разработчики реализуют расчет по клирингу, который происходит через несколько дней, это нарушит прямое требование извещать клиента «в момент покупки».

> «Дать клиенту возможность узнать о достижении личного бюджета в момент покупки.» — строка 23

> «В расходы входят проведённые покупки.» — строка 38

**Как исправить.** Заменить «проведённые покупки» на однозначный термин. Если важна моментальность, указать: «В расходы входят успешно авторизованные покупки».

**Вопрос автору.** Расчет расходов должен учитывать покупки в момент авторизации (холдирования) или только после клиринга (финансового списания)?

#### D-002. Отсутствует параметр для суммы за месяц

Критерий: полнота (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: критичный · Требования: R-002, R-011, R-030

Требования к UI указывают, что на экране отображается «сумма за месяц», а приложение получает данные через API из дочернего документа. Однако в параметрах ответа API (ни при успехе, ни при ошибке) нет поля, возвращающего текущие накопленные расходы. Разработчику фронтенда неоткуда получить это значение для вывода на экран, что блокирует реализацию интерфейса.

> «Карты → Расходы → Уведомления. На экране видны переключатель, поле «Порог, ₸», сумма за месяц и кнопка «Сохранить».» — строка 29

> «Приложение читает и сохраняет настройки через дочерний документ «Уведомление о расходах по карте — REST API».» — строка 52

> «amount · string · При успехе · Порог в тенге · limit_kzt» — строка 156

> «enabled · string · «0» или «1» · Признак включения · enabled» — строка 157

**Как исправить.** Добавить в ответ существующего API параметр для суммы за месяц, либо явно указать другой метод для получения текущих расходов по карте.

**Вопрос автору.** Через какой метод API мобильное приложение должно получать сумму расходов за месяц?

#### D-005. Неясно, какая сумма передаётся в push

Критерий: однозначность (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.2) · Серьёзность: критичный · Требования: R-008

Слово «сумму» можно интерпретировать по-разному: это может быть сумма текущей операции (покупки), общая сумма накопленных расходов за месяц или размер установленного порога. Неясно, какое значение сервис расходов должен передавать для отправки.

> «Сервис расходов → push: передать последние четыре цифры карты и сумму при достижении порога.» — строка 43

**Как исправить.** Уточнить, какая именно сумма передаётся, например: «...и накопленную сумму расходов за месяц при достижении порога».

**Вопрос автору.** Какую сумму нужно передавать в сервис push: сумму последней покупки, общие расходы за месяц или сам порог?

#### D-009. Нет правила для нового порога ниже текущих расходов

Критерий: полнота (ISO/IEC/IEEE 29148:2018, п. 5.2.5; IEEE Std 830-1998, п. 4.3.3) · Серьёзность: существенный · Требования: R-007

Требование Ф-4 описывает логику только для случая, когда накопленная сумма строго ниже нового порога. Неясно, как должна вести себя система, если пользователь задает порог, который уже равен текущим расходам или меньше их: отправить push немедленно при сохранении настройки или не отправлять ничего.
